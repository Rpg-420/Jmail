# مرجع API جی‌میل

> نسخهٔ فارسی؛ متن انگلیسیِ اصلی در `docs/API.md` است و همان مرجع فنی محسوب می‌شود.

جی‌میل یک میل‌سرور خصوصی است که روی لایهٔ رایگانِ Cloudflare می‌دود. پروژه‌های دیگر با یک توکن bearer و روی HTTPS ساده به آن وصل می‌شوند — نه پورت SMTP، نه کتابخانهٔ SMTP، و نه هیچ اتصال خروجی‌ای که خودت مدیریتش کنی.

- آدرس پایه: `https://<your-worker-or-domain>/api/v1`
- نوع محتوا: `application/json` (UTF-8) در همه‌جا
- احراز هویت: `Authorization: Bearer jmail_<secret>`
- بازرسی سلامت (بدون احراز هویت): `GET /api/health`

همهٔ آنچه در ادامه می‌آید را خودِ Worker اعمال می‌کند، نه عرفِ کار.

---

## 1. دریافت توکن

توکن‌ها را در رابط کاربری وب، از مسیر **Mail server → Project tokens** (`/mail-server`) بساز، یا با کوکی نشست خودت:

```bash
curl -X POST https://mail.example.com/api/tokens \
  -H "Authorization: Bearer <your web session token>" \
  -H 'Content-Type: application/json' \
  -d '{"name":"billing-app","scopes":["send","status"],"identity_address":"billing@example.com","rate_per_min":30,"daily_budget":200}'
```

(توکن نشست همان است که رابط کاربری وب پس از ورود در `localStorage.jmail_token` نگه می‌دارد؛ کارش احراز هویت نقاط پایانی مدیریتی است. توکن‌های یکپارچه‌سازی یک دستهٔ جداگانه‌اند و فقط روی `/api/v1` کار می‌کنند.)

پاسخ، مقدار `secret` را **فقط یک بار** دارد — آن را به‌صورت هش SHA-256 ذخیره می‌کنیم، پس هیچ‌وقت دوباره نمایش داده نمی‌شود. اگر گم شد، توکن را باطل کن و یکی تازه بساز.

| فیلد | بازه | معنا |
| --- | --- | --- |
| `name` | حداکثر 60 نویسه | در رابط کاربری نمایش داده می‌شود؛ به‌عنوان برچسب هم روی هر نامه‌ای که این توکن می‌فرستد اعمال می‌شود |
| `scopes` | `send`، `read`، `status` | پیش‌فرض `["send","status"]` |
| `identity_address` | نشانی یا `null` | فرستنده را قفل می‌کند: این توکن فقط با همین نشانی می‌تواند نامه بفرستد |
| `rate_per_min` | 1 تا 120 (پیش‌فرض 60) | پنجرهٔ لغزنده، به‌ازای هر توکن |
| `daily_budget` | 1 تا 5000 (پیش‌فرض 200) | تعداد ارسال در هر روز UTC؛ نیمه‌شب UTC صفر می‌شود |

**دامنه‌های دسترسی**

| دامنهٔ دسترسی | چه چیزی را اجازه می‌دهد |
| --- | --- |
| `send` | `POST /send` |
| `read` | نامهٔ ورودی: متن‌ها، پیوست‌ها، دانلود `.eml`، علامت‌گذاری به‌عنوان خوانده‌شده |
| `status` | `GET /quota` |

همهٔ نقاط پایانی زیر `/api/v1` به توکن نیاز دارند. هیچ دسترسی ناشناسی وجود ندارد، و حدس‌های ناموفقِ توکن به‌ازای هر IP محدود می‌شود (100 تلاش در 15 دقیقه).

## 2. ارسال: `POST /api/v1/send`

```json
{
  "to": ["customer@example.com", {"email": "alice@client.dev", "name": "Alice"}],
  "cc": "bob@client.dev",
  "subject": "Invoice 42",
  "text": "Plain text body",
  "html": "<p>HTML body</p>",
  "from": "billing@example.com",
  "reply_to": "replies@example.com",
  "headers": { "X-Invoice-Id": "42" },
  "attachments": [{ "filename": "invoice.pdf", "content": "JVBERi0xLjQK…", "content_type": "application/pdf" }],
  "labels": ["invoices"],
  "idempotency_key": "invoice-42-first-send",
  "send_at": "2026-11-02T09:00:00Z"
}
```

| فیلد | اجباری | توضیح |
| --- | --- | --- |
| `to` | بله | رشته یا آرایه‌ای از رشته‌ها یا `{email, name}`. حداکثر **50** گیرنده مجموعاً در `to+cc+bcc` |
| `subject` | بله | حداکثر **998** نویسه |
| `text` / `html` | حداقل یکی | `text` حداکثر 1 MB و `html` حداکثر 2 MB. عیناً ارسال می‌شوند — HTML خودت را خودت پاک‌سازی کن |
| `from` | نه | الزامی است مگر آنکه توکن به یک نشانی هویت قفل شده باشد — نشانیِ پیش‌فرض وجود ندارد، پس حذف‌کردنش `400` می‌گیرد. مگر توکن قفل‌شده باشد، باید یکی از نشانی‌های From تنظیم‌شده باشد |
| `cc`، `bcc` | نه | همان قالب‌های `to` |
| `reply_to` | نه | به شکل `replyTo` هم پذیرفته می‌شود |
| `headers` | نه | حداکثر 20 مورد. بخش 5 را ببین |
| `attachments` | نه | Base64. حداکثر 10 فایل، هرکدام 5 MB، مجموعاً 10 MB (قابل تنظیم توسط مدیر) |
| `labels` | نه | حداکثر 20 برچسب که هرکدام تا 40 نویسه؛ نام توکن همیشه اضافه می‌شود |
| `idempotency_key` | نه | حداکثر 120 نویسه، مختص توکن خودت. بخش 4 را ببین |
| `send_at` | نه | ISO-8601 آینده. زمان‌های گذشته رد می‌شوند |

### پاسخ‌ها

| Status | بدنه | معنا |
| --- | --- | --- |
| `200` | message + `provider`، `provider_message_id` | یکی از رله‌ها نامه را پذیرفت |
| `200` | message + `deduplicated: true` | کلید خودتوانی قبلاً استفاده شده بود؛ هیچ چیز دوبار ارسال نشد |
| `202` | message + `status: "queued"`، `retrying: true`، `reason` | ذخیره شد و به‌صورت خودکار دوباره تلاش می‌شود — همین حالا ظرفیت رله‌ها پر است، یا رله‌ای از دسترس خارج شده |
| `202` | message + `status: "queued"` | cron صف همین ردیف را وقتی این درخواست در جریان بود claim کرده؛ همان نوبت آن را تحویل می‌دهد |
| `202` | message + `queued_for` | ارسال زمان‌دار؛ صف در `send_at` آن را می‌فرستد |
| `400` | `invalid_request` | اعتبارسنجی رد شد؛ تنها راه‌حل، اصلاح بدنهٔ درخواست است |
| `401` | `unauthorized` | توکن غایب، ناشناس یا باطل‌شده |
| `403` | `forbidden`، `identity_mismatch`، `unverified_sender` | مشکل دامنهٔ دسترسی، نشانیِ قفل‌شده، یا فرستندهٔ ناشناس |
| `422` | `rejected_by_relay` | خودِ رله این نامه را رد کرده. دوباره‌تلاش فایده‌ای ندارد |
| `429` | `rate_limited` یا `budget_exceeded` | آرام‌تر؛ `retry_after` می‌گوید کِی |

`GET /api/health` مقدار `next_utc_midnight` را به ثانیه برمی‌گرداند — شمارنده‌های خودت را همان لحظه‌ای صفر کن که سمت سرویس‌دهنده صفر می‌شود.

### پاسخ `202` برای داده‌های تو چه معنایی دارد

هیچ چیز از دست نمی‌رود. ردیفِ `202` در صف ارسال می‌ماند و با پلکانِ بازتلاش (30 ثانیه → 2 دقیقه → 5 دقیقه → … → 24 ساعت، در مجموع 10 تلاش) جلو می‌رود؛ cron به‌محض اینکه یک رله ظرفیت آزاد داشته باشد آن را تحویل می‌دهد. ردیف‌هایی که پس از بازهٔ نگهداری (`queue_retention_days`، پیش‌فرض 14) هنوز تحویل نشده‌اند `failed` می‌شوند و یک وب‌هوک `failed` زده می‌شود.

در هر لحظه فقط یک نوبتِ drain مالک یک ردیف است: هرکس ردیف را claim کند قفل زمان‌دار 10 دقیقه‌ای دارد، پس یک نوبتِ cronِ همپوشان یا درخواستی که با cron رقابت کند نمی‌تواند یک نامه را دو بار بفرستد. اگر Worker بعد از اینکه رله نامه را پذیرفت ولی پیش از ذخیرهٔ نتیجه کشته شود، قفل زمان‌دار آزاد می‌شود و ارسال دوباره تلاش می‌شود — در آن حالت نادر، تحویل حداقل-یک‌بار است، پس همیشه `Idempotency-Key` بفرست و سمت خودت با شناسهٔ نامه تکراری‌ها را حذف کن.

## 3. خواندن نامه‌ها: `GET /api/v1/messages`

نامه‌های خروجی که **توکن خودت** فرستاده همیشه برای خودت قابل مشاهده‌اند. برای نامهٔ ورودی دامنهٔ دسترسی `read` لازم است.

```bash
curl -H "Authorization: Bearer $JMAIL_TOKEN" \
  'https://mail.example.com/api/v1/messages?limit=20&status=delivered'

curl -H "Authorization: Bearer $JMAIL_TOKEN" \
  'https://mail.example.com/api/v1/messages?direction=inbound&unread=true&label=support'
```

پارامترهای کوئری: `limit` (1 تا 100، پیش‌فرض 25)، `offset`، `status`، `idempotency_key`، `direction=inbound`، `unread=true`، `label`.

نمای نامه (هم در فهرست و هم تک‌به‌تک):

```json
{
  "id": "0f5c…", "direction": "outbound", "from": "billing@example.com",
  "to": "customer@example.com", "cc": null, "subject": "Invoice 42",
  "status": "delivered", "provider": "brevo", "attempts": 1, "last_error": null,
  "labels": ["billing-app"], "message_id": "<…>", "thread_id": "<…>",
  "created_at": "2026-10-28 09:12:33", "scheduled_at": "2026-10-28 09:12:33"
}
```

متن نامه‌ها هرگز در فهرست نمی‌آید. برای دیدنشان یک نامه را جداگانه بگیر:

| نقطهٔ پایان | دامنهٔ دسترسی | چه برمی‌گرداند |
| --- | --- | --- |
| `GET /messages/:id` | مالک نامه، یا `read` برای نامهٔ ورودی | نمایِ نامه؛ اگر دامنهٔ `read` روی نامهٔ ورودی باشد، `text`، `html`، `headers`ِ امن و اطلاعات پیوست‌ها هم اضافه می‌شوند |
| `GET /messages/:id/attachments/:attachmentId` | `read` | بایت‌های خام با `Content-Disposition` |
| `GET /messages/:id/eml` | `read` | دانلود به شکل `message/rfc822` |
| `POST /messages/:id/read` | `read` | `{success: true}` |

شناسهٔ نامه‌ای که به توکن دیگری تعلق دارد به‌جای `403` پاسخ `404` می‌دهد — API تأیید نمی‌کند که نامهٔ کس دیگری وجود دارد.

## 4. کلید خودتوانی

`idempotency_key` تلاش‌های دوباره روی شبکهٔ بی‌ثبات را یکی می‌کند. جست‌وجو فقط داخل توکن خودت انجام می‌شود، پس دو پروژه می‌توانند از یک کلید استفاده کنند و به هم نمی‌خورند.

- اولین فراخوانی با یک کلید: ارسال معمولی.
- هر فراخوانیِ بعدی با همان کلید: پاسخ `200` با نامهٔ اصلی و `deduplicated: true`. بدون تماس با رله، بدون مصرف سهمیه.
- کلیدها همراه نامه نگه داشته می‌شوند، نه در یک کشِ کوتاه‌عمر — تلاش دوباره یک ساعت بعد هم امن است.

از یک شناسهٔ کسب‌وکاری (`invoice-42-password-reset-2026-10-28`) استفاده کن، نه یک UUID تصادفی؛ وگرنه این تضمین بی‌ارزش است.

## 5. هدرهای سفارشی

فقط این‌ها را فراخوان می‌تواند تنظیم کند:

- هر نامی که با `x-` شروع شود
- `Reply-To`، `In-Reply-To`، `References`

هر چیز دیگری با `400` رد می‌شود، از جمله `From`، `To`، `Cc`، `Bcc`، `Subject`، `Content-Type`، `MIME-Version`، `Message-ID`، `Date`، `Sender`، `Return-Path`، `Received` و `DKIM-Signature`. مقادیر هدری که CR یا LF داشته باشند کامل رد می‌شوند، پس بدنهٔ درخواست هیچ‌وقت نمی‌تواند هدر یا گیرندهٔ اضافه تزریق کند.

`Reply-To` داخل درخواست رله کپی می‌شود، پس زنجیره‌سازی (threading) و مسیر برگشتِ نامه‌ها همان‌طور رفتار می‌کند که پروژهٔ تو انتظار دارد.

## 6. سهمیه: `GET /api/v1/quota`

دامنهٔ دسترسی `status` لازم دارد.

```json
{
  "day": "2026-10-28",
  "token": { "name": "billing-app", "daily_budget": 200, "sent_today": 12, "failed_today": 1, "remaining_today": 187, "rate_per_min": 30 },
  "providers": [{ "id": "brevo", "label": "Brevo", "quota_day": 300, "used_day": 88, "remaining_day": 212 }],
  "total_remaining_today": 212
}
```

سه بودجهٔ مستقل همیشه حاکم‌اند و سخت‌گیرانه‌ترینشان برنده می‌شود:

1. **بودجهٔ روزانهٔ توکن خودت** — به‌ازای هر پروژه، پس یک اپِ سرکش نمی‌تواند کل صندوق را خالی کند.
2. **سهمیهٔ روزانهٔ رایگان هر رله** — Brevo در برنامهٔ رایگان 300 در روز و Resend 100 در روز. جی‌میل مصرف را محلی ردیابی می‌کند و نامه را به رله‌ای که سهمیهٔ روزش تمام شده اصلاً پیشنهاد نمی‌دهد. سقفِ ماهانه (Resend ماهی `3 000` را هم سقف می‌کند) فقط اگر خودت تنظیمش کنی اعمال می‌شود: تنظیم `provider_quota_resend_month` را روی `3000` بنویس تا آن عدد هم وارد بررسی شود.
3. **سقف درخواست‌های Worker** — لایهٔ رایگان کلودفلر: `100 000` درخواست در روز، CPU معادل 10 ms به‌ازای هر درخواست (انتظار شبکه حساب نمی‌شود).

وقتی سهمیهٔ همهٔ رله‌ها تمام شود، ارسال‌ها شکست نمی‌خورند: پاسخ `202` می‌گیرند و در صف می‌مانند، و صف به‌محض اینکه سهمیهٔ یک رله در نیمه‌شب UTC پر شود تخلیه می‌شود. اگر پروژه‌ات می‌خواهد پیش از آن‌وقت عقب بنشیند، `/quota` را poll کن.

## 7. وب‌هوک‌ها

جی‌میل رویدادهای تحویل را خودش به پروژهٔ تو می‌فرستد تا مجبور نباشی بپرسی (poll کنی). نقاط پایانی را در **Mail server → Webhooks** ثبت کن؛ بدنهٔ درخواست، روش امضا، کد راستی‌آزمایی برای هر زبان و پلکانِ بازتلاش در [WEBHOOKS.md](WEBHOOKS.md) مستند شده است.

رویدادها: `sent`، `delivered`، `opened`، `bounced`، `deferred`، `failed`، `received`.

---

## 8. شناسهٔ توکن و قفل فرستنده

توکنِ بدون‌قفل فقط می‌تواند از نشانی‌های From که در **Settings → Addresses** وجود دارند استفاده کند. توکنی که `identity_address` دارد هیچ‌وقت نمی‌تواند به‌عنوان کس دیگری نامه بفرستد — `from` را کلاً حذف کن تا همان نشانیِ قفل‌شده به کار می‌رود، یا صریحاً بفرست و API چک می‌کند که با آن بخواند (بدون حساسیت به بزرگی و کوچکی حروف).

برای پروژه‌ای که فقط با یک نشانی می‌فرستد، قفل کردن انتخاب امن‌تری است: توکنِ لو‌رفته نمی‌تواند هویت‌های دیگر تو را جعل کند.

---

## 9. فراخوانی از مرورگر

به‌جایش از بک‌اند خودت صدا بزن. `POST` بین‌مبدأ (cross-origin) طبق طراحی رد می‌شود (`routes.ts` هر درخواستی که GET نباشد و `Origin` آن میزبان خودِ میل‌سرور نباشد را رد می‌کند)، و توکن bearer در کد مرورگر یعنی توکنی که عمومی‌اش کرده‌ای. تنها استثنا توسعهٔ محلی روی `localhost:5173` است.

## 10. برگهٔ سقف‌ها

| چیز | سقف | چرا |
| --- | --- | --- |
| گیرنده در هر نامه | 50 | همهٔ رله‌های پشتیبانی‌شده ارسال رایگان را روی 50 محدود می‌کنند |
| موضوع | 998 نویسه | سقف هدر خروجی Email Routing در کلودفلر |
| بدنهٔ `text` / `html` | 1 MB / 2 MB | بودجهٔ حافظهٔ Worker به‌ازای هر درخواست |
| پیوست (فایل / مجموع / تعداد) | 5 MB / 10 MB / 10 | `10 MB base64 ≈ 13 MB JSON` و داخل سقف درخواست Worker جا می‌گیرد |
| کلید خودتوانی | 120 نویسه | ستون ایندکس‌شده |
| هدرهای سفارشی | 20 مورد، هرکدام 500 نویسه | بودجهٔ هدر که با رله مشترک است |
| نگهداری صف | 14 روز (قابل تنظیم) | نامهٔ غیرقابل‌تحویل نباید تا ابد بماند |

## 11. شکل خطاها

هر خطا JSON است با یک فیلد `error` ماشین‌خوان و یک `message` برای آدم:

```json
{ "error": "rate_limited", "message": "Token limit is 30 requests per minute", "retry_after": 41 }
```

| `error` | Status | دوباره‌تلاش؟ |
| --- | --- | --- |
| `invalid_request` | 400 | نه — بدنه را اصلاح کن |
| `unauthorized` | 401 | نه — توکن را چک کن |
| `forbidden` | 403 | نه — دامنهٔ دسترسی را اضافه کن |
| `identity_mismatch` | 403 | نه |
| `unverified_sender` | 403 | نه — نشانی را تنظیم کن یا توکن را قفل کن |
| `not_found` | 404 | نه |
| `rejected_by_relay` | 422 | نه — رله این نامه را رد کرده، `detail` را ببین |
| `rate_limited` | 429 | بله، بعد از `retry_after` ثانیه |
| `budget_exceeded` | 429 | بله، بعد از نیمه‌شب UTC |
| `storage_failed` / `attachment_unavailable` | 500 | بله — با همان کلید خودتوانی |

هر پاسخ `5xx` را قابل‌تلاشِ‌دوباره بگیر و کلید خودتوانی را نگه دار؛ همین ترکیب است که روی شبکهٔ بی‌ثبات تحویلِ دقیقاً-یک‌بار را برایت می‌سازد.
